# P7 求职工坊：三个 Agent 的求职匹配器

贴一份招聘 JD 和一份简历，输出：**匹配度打分、能力缺口、简历改写建议、面试准备题**。
重点不在产品本身，而在于把「多个 Agent 之间怎么传信息、信息在哪一步会丢」这件事走一遍。

把 P7 从「能跑」改造成「可度量」。指标口径、评估集、成本记账、结构化日志与回放全部落地，
详细定义见 [`docs/指标口径.md`](docs/指标口径.md)，实验数据见 [`docs/分级实验.md`](docs/分级实验.md)。

| 指标 | 改造前 | 改造后 |
|---|---|---|
| 评估得分 | 无评估集，说不清 | **12/12（100%）**，四项判据逐条可查 |
| 单次成本 | 不知道花了多少 | **¥0.0030**（千次 ¥3.01） |
| 平均延迟 | 只知道"有点慢" | **P50 2.7s**，各节点耗时在 `trace` 里 |

### 工程件

- `evaluate.py`：跑评估并报三个数，报告落 `eval/results/*.json`
- `test_structure.py`：结构回归（不调模型、零成本），CI 每次 push 跑
- `.github/workflows/`：push 跑结构回归；真模型评估手动触发（省 token）
- `main.py --replay runs/xxx.json`：回放任意一次历史运行
- 节点级开关 `P7_STUB_PARSER / P7_STUB_MATCHER / P7_STUB_ADVISOR`：分级实验用

### 分级实验结论（重要）

| 配置 | 通过率 | 单次成本 | 改写质量 |
|---|---|---|---|
| 全模型（基线） | 100% | ¥0.0030 | 2.00 / 2 |
| 解析员换规则 | 18% | ¥0.0014 | — |
| 解析+匹配换规则 | 0% | ¥0.0005 | — |
| **建议员换规则** | **100%** | **¥0.0024** | **0.33 / 2** |

前三个节点都不能降级。最后一行尤其值得注意：**四项判据显示「完全没变差」，
但改写质量从 2.00 掉到 0.33**——因为判据里没有「建议写得好不好」这一项。
指标没覆盖的地方，优化就会往那儿塌。

## 架构

```
              ┌──────────┐
JD + 简历 ───▶│ ① 解析员  │  按行切分 → 逐行分类 must/plus/skip
              └────┬─────┘
                   ▼
            ★ 人工确认点 1   可增删硬性条件（改动写入 edits 日志）
                   ▼
              ┌──────────┐
              │ ② 匹配员  │  逐条判定命中/部分/缺失，分数由本地公式算
              └────┬─────┘
                   ├── score < 40 且用户未选择继续 ──▶ 劝退（只给差距，不写建议）
                   ▼
            ★ 人工确认点 2   可划掉不认同的缺口，分数本地重算
                   ▼
              ┌──────────┐
              │ ③ 建议员  │  每条改写必须绑 gap_id + 简历原句 sid
              └────┬─────┘
                   ▼
        报告：匹配度 / 缺口 / 改写 / 5 道面试题 / 行动建议
```

编排器是代码（LangGraph 的图），模型只在节点内部做判断——流程不交给模型决定。

## 三个 Agent 的分工

| Agent | 自主判断 | 写死的约束 |
|---|---|---|
| ① 解析员 | 这一行算硬性、加分还是无关 | 按行切分（不由模型定粒度）；输出必须带原文 span |
| ② 匹配员 | 这条命中、部分命中还是缺失 | 分数公式固定（硬性 70 + 加分 30）；证据必须指向真实句子编号 |
| ③ 建议员 | 改哪句、怎么改、出什么题 | 改写必须绑 `gap_id` + `sid`；不得替候选人承诺简历里没有的信息 |

## 状态设计（核心）

只有一份 state，全程「只增不改」：

```python
{
  "run_id": "...", "status": "running|done|abandoned",
  "input":  {"jd": "...", "resume": "..."},          # 原始输入，永不修改
  "job":    {"rev": 1, "must": [...], "plus": [...]}, # 解析员写一次
  "edits":  [{"point": 1, "target": "job.must", ...}],# 人审改动只追加到这里
  "match":  {"rev": 1, "job_rev": 1, "score": 64, ...},# 带版本锚点
  "advice": {"rev": 1, "match_rev": 1, ...},
  "trace":  [...], "errors": [...]
}
```

三条规则：

1. **改的是日志，不是状态**：人审改条件写 `edits`，下游读 `fold(job, edits)`，`job` 本体保留模型原始输出，便于复盘对比
2. **每条结论带版本锚点**：`match.job_rev` 与当前 `job.rev` 对不上就说明上游变了，必须重跑
3. **证据按编号取**：模型只说「第几句」，原文由程序取，杜绝「模型回抄文本导致变形」

## 怎么跑

```bash
python -m venv .venv
.venv/Scripts/pip install -r requirements.txt
# 需要环境变量 LLM_API_KEY（DeepSeek）

.venv/Scripts/python main.py --jd data/jd/1.md --resume data/resume.md          # 交互版（两个暂停点）
.venv/Scripts/python main.py --jd data/jd/1.md --resume data/resume.md --auto   # 自动跑完
.venv/Scripts/python main.py ... --add-must "必须会 Go 语言"                     # 验证版本传导
.venv/Scripts/python main.py ... --reject g1                                   # 划掉某条缺口
```

## 三个真实踩坑（信息交接）

完整记录见 [`docs/联调记录.md`](docs/联调记录.md)，摘要：

1. **模型自己决定切几条，同一个 JD 分数会抖**：连跑三次硬性条件是 4/4/6 条，合并那次「学历」盖住了「专业不符」，错误延迟到第三环才显形。修法：代码按行切分，模型只做分类。
2. **让模型回抄原文不可靠**：它会把句子标签一起抄进来，逐字校验全灭，64 分被打成 0 分。修法：只回句子编号。
3. **模型会替候选人编承诺**：「可保证每周到岗 5 天」——简历里没有。修法：提示词禁止 + 数字防伪校验兜底。

## 已知局限

- 中文数字（十万/三千）未纳入防伪校验，模型可能夸大数量级
- 加分项与硬性条件的权重（30/70）是主观设定，未调参
- 只支持单份简历单份 JD，没有批量与并发测试
- 命令行界面，无 Web UI
