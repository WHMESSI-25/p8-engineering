# P8 指标口径（v1，2026-11-04）

> 这份文件是 P8 的地基：**先定义怎么算，再谈优化。**
> ROADMAP 的验收只有一句——能报出「单次成本、评估得分、平均延迟」这三个数。
> 口径一旦定下，后面所有对比都要按它算，不许中途改定义。

---

## 一、什么算「一次成功」

一个 case 跑完，**四项全中才算 1 分**，否则 0 分（不设半分，避免自我安慰）：

| # | 判据 | 怎么判 | 为什么这么定 |
|---|---|---|---|
| 1 | **硬性条件抽全** | 人工标注的每条期望条件，都要能在 `job.must` 里找到关键词命中 | 抽漏一条，后面全错；这是整条链的入口 |
| 2 | **缺口不遗漏** | 标注的每条期望缺口，都要出现在 `match.gaps` 的描述里 | 「没报出来的问题」比「报错了」更危险 |
| 3 | **零编造** | `errors` 里没有 `possible_fabrication` / `ghost_gap_ref` | 编造是产品事故，不是质量问题 |
| 4 | **分数落区间** | `match.score` 落在人工标注的 `[lo, hi]` 内（区间宽度 ±10） | 分数是用户第一眼看到的结论 |

**评估得分 = 通过数 / 总 case 数。**

> 为什么不用「看起来不错」：那种标准两个人看同一份输出能吵起来，也没法做前后对比。

---

## 二、单次成本怎么算

按 DeepSeek 官方单价折算（`deepseek-chat` = V4-Flash 非思考模式）：

```
输入：$0.14 / 百万 tokens
输出：$0.28 / 百万 tokens
汇率：按 7.1 折算成人民币（可配置，见 evaluate.py 的 PRICE 常量）
```

单 case 成本 = Σ(每个节点 prompt_tokens × 输入价 + completion_tokens × 输出价)

**报三个层次**：

1. 单 case 成本（¥/case）—— 用于和别的方案对比
2. 1000 次成本（¥）—— 用于跟人解释「这玩意用起来多贵」
3. 各节点占比 —— 用于判断该优化谁（比如解析员占 60% token，就优先砍它）

不统计缓存命中（DeepSeek 有前缀缓存，实际会更便宜），**报的是保守上界**。

---

## 三、延迟从哪算到哪

**端到端**：从读入 JD/简历，到产出最终 `advice`，包含三次 LLM 调用，**不含人工暂停**（评测时自动跳过两个人审点）。

- 主指标：**P50**（中位数），避免被个别超时拉偏
- 附指标：P90、各节点耗时中位数（来自 `trace`）

不把「首字延迟」算进来——这是批量任务，不是聊天。

---

## 四、怎么对比才有效

| 做法 | 允许 | 说明 |
|---|---|---|
| 同一份评估集、同一套标注 | ✅ | 换方案必须锁死输入 |
| 只改一个变量 | ✅ | 比如只把解析员换成规则版，其他不动 |
| 同时改三处再报总分 | ❌ | 涨了也不知道是谁的功劳 |
| 只报总分不报分项 | ⚠️ | 必须同时给出四项判据的通过数，否则看不出退步在哪 |
| 报「明显变好了」 | ❌ | ROADMAP 明令禁止：没有数字不算结论 |
